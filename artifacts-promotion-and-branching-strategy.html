Challenge 2: Env Config Branch-Coupled & Baked into Image

Problem

Some environment config is branch-coupled and baked into the Docker image at build time , a different image is produced per branch, so the same artifact cannot be promoted.

Evidence , build.properties (estv-calcavailablevisas)
applicationName=CalculateAvailableVisas shared-lib=Framework,EstablishingVisasManagementLib common-lib=MQPolicyProject,BackendAdaptersLib,HRSDLib additional=com.qiwa.esb.calculateavailablevisas.\ GW_Rest_CalculateAvailableVisasFlow#additionalInstances=10,\ CalculateAvailableVisasFlow#additionalInstances=10

Source: build.properties , branch-specific assembly config per service

Impact
  • Cannot promote the same image across environments , must rebuild per branch
  • staging branch → image A  |  preprod → image B  |  main → image C
  • 3 branches = 3 different artifacts for identical business logic
  • Additional instances (#additionalInstances) differ per branch → runtime behaviour changes

"Tested on staging" does not mean prod will behave the same , different image, different config, different library versions.

Challenge 6: Inconsistent Deployment Mechanisms

Staging path (imperative):
oc apply -f ACE_Deployment.yaml
oc create configmap $MODULE-pp-props-cm --from-file=workspace/properties/ -o yaml --dry-run=client | oc apply --server-side=true --force-conflicts -f -
CI runner holds cluster credentials. No GitOps trail. State can drift undetected.

Preprod also uses oc apply for configmap:

Semantic Versioning & Tagging , Libraries

From , Cloning Libraries by Branch

# prepare-workspace.yml — today
git clone ... common-lib.git -b $CI_COMMIT_BRANCH
git clone ... shared-lib.git -b $CI_COMMIT_BRANCH
→ staging build uses staging branch
→ preprod build uses preprod branch
→ prod build uses main branch
→ 3 envs, 3 different library realities

The same release is built with different library code depending on the environment

To , Using Versioned Libraries

# build.properties — pinned per release
common-lib-version=v2.1.0
shared-lib-version=v1.5.0
# prepare-workspace.yml — proposed
git clone ... common-lib.git -b $(common-lib-version)
git clone ... shared-lib.git -b $(shared-lib-version)
→ staging, preprod & prod use exact same versions

Library versions are an explicit, reviewable decision in every MR

Result: For each release, the same library versions (common-lib=v2.1.0, shared-lib=v1.5.0) are used consistently across all environments — staging, preprod and prod build from identical library code.

De-couple Configuration from Code

One BAR file for all environments — service-specific overrides via ACE Configuration CRD

From , Per-service build.properties

# build.properties — baked into image per branch additional=com.qiwa.esb.calculateavailablevisas.GW_Rest_CalculateAvailableVisasFlow #additionalInstances=10 # Rebuild required per environment # Cannot promote the same image

additionalInstances is baked into the image — changing it means a full rebuild and re-test cycle

To , ACE Configuration CRD (workdiroverride)

# 1. Configuration CRD — applied per service per env apiVersion: appconnect.ibm.com/v1beta1 kind: Configuration metadata: name: serviceworkdiroverride namespace: ace spec: type: workdiroverride data: <Base64-encoded overrides> description: "Workdir overrides for additionalInstances"
# 2. IntegrationServer references the Configuration apiVersion: appconnect.ibm.com/v1beta1 kind: IntegrationServer metadata: name: sample-integration-server namespace: ace spec: configurations: - serviceworkdiroverride

Same image promoted through all environments — override applied at runtime

Note: Configuration types include serverconf, policyproject, setdbparms, keystore, truststore, odbc, generic, and agentx

GitOps & ArgoCD Structure

Current

deployments/ ├── pipeline-prd-12345/ ← stale ├── pipeline-prd-12346/ ← stale ├── pipeline-prd-12347/ ← stale 5,000+ stale branches # Every service has a full copy service-a/ACE_Deployment.yaml ← 300+ files, 90% identical # ArgoCD apps created manually, one by one # New service = manual ArgoCD app creation

Key decision in progress: Versioned template tool — Helm (values-based, wider ecosystem) vs Kustomize (pure YAML patches, no templating layer, native to ACE CRDs). Either solves the 300+ duplication problem. ApplicationSet approach works with both.

Solution: Consolidation & Standardisation

Unified GitOps , ApplicationSet

# One ApplicationSet auto-manages all services kind: ApplicationSet spec: generators: - git: directories: - path: services/*/* template: spec: source: targetRevision: HEAD
  • New service folder → ArgoCD app auto-created
  • No manual app wiring per service
  • Staging = same model as preprod & prod

Versioned ACE Template (Helm / Kustomize TBD)

# common-cicd — one versioned template ace-template:v1.0.0 → IntegrationServer base → resources, probes, annotations # Each service — only what differs service-a/values.yaml: name: service-a image: ...registry.../ace/...:v1.2.0 replicas: 2
  • 300+ full YAMLs → 1 versioned template
  • Service onboarding = minimal values file

Shared ConfigMap

# 1 common-lib-cm — all services # 1 shared-cm per module configmaps/ ├── common-lib-cm.yaml ├── shared-lib-cm.yaml # Services reference, not own configurations: - common-lib-cm - shared-lib-cm
  • 2 CMs
  • No pipeline re-run for config changes

Implementation Phases

Phase 1 , Pilot

Run on a selected set of services — prove the model before full rollout

  • Library versioning: pin common-lib & shared-lib by semver tag in build.properties; stop cloning by $CI_COMMIT_BRANCH
  • Branch consolidation: devs work on main + feature/* branches; owner cuts release/* branch per release cycle
  • CI/CD refactor: unify GitOps deployment across all environments including staging (remove oc apply, push to ArgoCD repo for all envs)
  • Pilot success metrics: define before starting: build stability, deployment consistency, lead time .. etc

Phase 2 , Scale Rollout

Apply lessons from pilot to the next set of services — module by module

  • Roll out to next module using validated model from Phase 1
  • Migrate ArgoCD apps to ApplicationSet and AppofApps
  • Introduce versioned ACE template , replace 300+ full YAMLs
  • Consolidate duplicated ConfigMaps to shared CMs
  • Continue module by module until all services migrated
